# Rules for Agents

This is the monorepo for OCM Fleet, an experimental Open Cluster Management variant using a resource manager architecture. It contains the resource manager server, CLI, proto definitions, React web UI, addons, and proof-of-concept experiments.

## Nx

- Run workspace tasks (build, test, lint, proto, image, infrastructure) through the repository's Nx CLI: `npx nx`. Deployment scripts provide platform-specific checks.
- Prefer `NX_DEFAULT_OUTPUT_STYLE=summary npx nx ...` to limit output, including from nested Nx invocations. Check the exit status and summary; on failure, inspect the reported log selectively, following nested log paths as needed. Successful task output is suppressed. Use `--outputStyle=static` when inline output is needed.
- Iterate with the relevant test target; finish with `npx nx run <project>:verify` (format/import fixes, lint, and available tests/type checks). Use `npx nx run ocm-fleet:verify` across projects; Go-only tasks retain the `:go` suffix. Integration and end-to-end suites stay explicit.
- Broader linter fixes are opt-in: `npx nx run <project>:fix`; review the diff.
- For new projects or quality targets, follow [the Nx project setup guide](docs/nx-projects.md); `ocm-fleet:lint:nx-projects` checks participation and shared task policy.

## Understanding the domain

OCM Fleet’s resource manager owns APIs, authorization, persistence, and orchestration. Fulfillments combine manifest, placement, and rollout strategies. Addons provide domain-specific behavior; fleetlets provide shared connectivity and delivery checks. CLI and web clients share a common core and extension mechanism.

Consult these for design tasks, or when a specific reference is needed for changes in that subsystem. Paths below are relative to `docs/design/`.

- `glossary.md`: Component names and architectural boundaries

## Cross-cutting concerns (very important)

- This is still experimental. Don't be afraid to break contracts if it would produce a more ideal design for the task at hand. We'd rather learn and experiment with a potentially better way. There's little value to backwards compatibility for compatibility's sake.
- _Please don't casually remove comments unless they are truly no longer relevant_ (e.g. a TODO that is now implemented or obsolete, or out of date explanations). Prefer updates to removal, unless behavior is obvious from the code or signature.
- Keep design documentation up to date, but focused on the design and vision. _Do not overfit design documentation to the code, specific API, or current implementation_. It is a guide for how we intend the implementation to evolve, more than it is a description of its current state. We should update them when, during the course of implementation and planning, we realize that the design and vision itself should change, or has become out of alignment with what we are building in non-temporary ways. References to code or API are far from forbidden, but just used judiciously, to tie the desired design to the prototype.
- To document the code and implementation itself, prefer readable, self-describing code and inline comments
- Prefer modern standard library abstractions and utilities, or well justified inclusion of established libraries, over custom implementations
- Follow test-driven development. When at all possible, write failing tests **first**, then write the code to make the test pass.
