# OME AIO Installation Check CLI

**Status:** PoC implementation validated on macOS. Product-policy decisions and cross-platform validation remain open.

## Purpose

Provide an OME-branded utility to check host readiness for the FleetShift all-in-one (AIO) container, explain issues, apply approved fixes, and optionally prepare and execute a launch command. Preflight establishes host readiness; image pulling occurs only at launch.

The central proof-of-concept objective is to compile and run this interactive TypeScript utility as a standalone native executable with Ink. The PoC validated Perry 0.5.1520 as its native compiler. ScriptC 0.3.1 was the initial candidate, but its Ink/React compatibility blockers mean ScriptC is not a PoC or product-release gate. Native execution remains the requirement; compiler choice for a distributable product remains subject to release review.

See the [companion decision note](./aio-installation-check-decisions.md) for compiler selection, Ink/Perry UI layering, Rust build dependencies, and native compatibility shims.

## Scope

- **First release:** macOS and Linux; local Podman or Docker; default AIO and optional `--with-kind` checks; lightweight Ink-based terminal UI; remediation; optional launch and `/data` persistence.
- **Packaging and reuse:** The utility MUST ship as a native executable that runs without a separately installed Node.js. The validated PoC compiler is Perry 0.5.1520; Node.js, Rust/Cargo, and a matching Perry source checkout are currently needed to build it. ScriptC was evaluated but its build dependency and targets are not retained in the current PoC. No dynamic plugins. UI-free checks remain individually callable, separate from the entrypoint, for possible future `fleetctl` diagnostics. The separate utility does not implement existing `fleetctl` management commands or integrate with it in this release. Host Node.js guidance concerns `fleetctl` only.
- **Deferred:** Windows (revisit after the distribution model is understood), npm/npx execution, public npm publication, Homebrew release, general multi-architecture distribution, and JSON/non-interactive mode.
- **Excluded:** IdP/OIDC setup and non-core extension configuration checks, including GCP HCP as an ordinary example, not a special case. Launch requires explicit approval of the displayed command.

## Users and terminology

- **User:** Person preparing a host; **utility:** the standalone preflight CLI.
- **`fleetctl`:** Existing Node.js-based FleetShift CLI; cannot run without Node.js. Node 24 is the specified minimum; older versions are unsupported, not proven unable to execute it.
- **Runtime:** Podman or Docker, including its service/context and socket where relevant.
- **Kind mode:** Local Kubernetes checks requested with `--with-kind`. Kind is the first supported distribution, not a non-core extension here; Minikube and other distributions may follow.
- **Fix:** A host setup action or user-executable command that addresses a failed check.

## Context and constraints

- The [AIO README](../../deploy/aio/README.md) documents Podman as tested, IPv4 loopback ports `127.0.0.1:8085` and `127.0.0.1:50051`, and no engine socket for basic AIO. Kind adds a live socket at `CONTAINER_HOST`, `/tmp`, the `kind` network and `fleetshift` alias, and `--privileged`. Keep that local/development invocation and explain broad host access without asserting privilege is technically necessary. Linux rootless Podman's socket uses a user systemd service.
- The local-only policy covers Docker Desktop's local context and Podman's managed local machine/Linux engine; arbitrary remote engines are outside first-release support. Docker remains selectable with a project-validation warning, not a presumed defect.
- **Snapshot (2026-10-14):** Podman client 5.8.1/server 5.8.5; Docker client/engine 28.0.4, Desktop 4.40.0; Node.js 26.8.1; Docker context `desktop-linux`; running local Podman machine: 6 CPUs, 19,953 MiB memory, 150 GiB disk. Runtime versions are informational. These observed resource values are agent-derived, unconfirmed proposed warning floors, not an agreed threshold policy (REQ-045).
- Node 24 is LTS and Node 26 is Current, not LTS, as of that date. The `fleetctl` support minimum is Node 24; Node 26 is eligible. Missing/unsupported Node.js never blocks AIO.
- **Native compiler:** Perry 0.5.1520 currently builds the standalone executable and runs the interactive Ink-based flow on macOS. The single Nx build command manages the matching source checkout and pinned Rust/Cargo toolchain for missing support archives. Linux also builds the compiler from that same clean checkout to avoid the npm compiler's runtime source-hash mismatch, using installed LLVM 22 development libraries or a SHA256-verified official bundle. Native C/linker SDK and system dependencies remain prerequisites; builds target the host CPU and glibc/distribution baseline. The compiler and application built on Fedora 44 ARM64, and direct execution rendered readiness; Linux x86_64, full Linux interactive checks, and run-without-Node acceptance remain unverified. See the [decision note](./aio-installation-check-decisions.md#build-time-rust-and-native-code) for details. ScriptC 0.3.1 was evaluated and rejected for this PoC because its current Ink/React package graph and relevant Node API call shapes have unresolved compilation blockers; its compiler dependency and build targets were removed. Keep Ink rendering and the native-executable requirement; do not replace the executable with a Node-launched CLI. Perry uses its native Unix-socket transport without a curl runtime dependency.
- Documentation links may remain placeholders until a public site exists. Manual-fix polling is specified in REQ-019/036; unresolved timing interpretation is listed under Remaining validation and decisions.

Runtime notes:

- Docker is not known to have a specific defect in this AIO path; current warning represents missing project validation. A passing `docker info` means the Docker engine is reachable, not that every Kind/AIO integration has been tested. Keep Docker selectable and do not convert the validation warning into a failure.
- On macOS, `podman machine start` can report the forwarded API socket and indicate whether `podman-mac-helper` is missing. This forwarded path is a host API endpoint, not the VM-side bind source. A running machine and host ping alone do not prove that the engine can bind the selected socket; validate its existence inside the matching machine. Use helper guidance rather than hard-coding its versioned install path.
- Runtime-specific launch syntax matters. Current documented Podman syntax uses `--network kind:alias=fleetshift`; Docker documents `--network kind --network-alias fleetshift`. Generate the selected runtime's syntax rather than reusing Podman arguments verbatim.
- A successful port-availability probe is a snapshot and can race with another process claiming the port before AIO launch.
- Further candidates to evaluate: image architecture compatibility; host-path sharing for `/tmp`, socket, and `/data`; network driver/alias behavior; Quay reachability during every `latest` pull; Linux rootless Podman kernel key quotas for larger Kind topologies. These remain warnings/investigation topics, not blockers, until additional thresholds are validated.

## Readiness classification

Host preflight requires:

- The selected local runtime passes its engine checks. Another usable runtime allows the user to switch and re-evaluate; it does not pass a failed selected engine. Podman is preselected when both are detected.
- Host ports `127.0.0.1:8085` and `127.0.0.1:50051` are available.

Launch setup additionally requires a usable `/data` host path only when persistence is selected. The image pull happens at launch, not preflight; its failure is a launch failure (REQ-055), not retroactive host incompatibility.

Additional blockers only when Kind mode is selected: a reachable engine API socket with an identified engine-side bind source mounted at AIO's `CONTAINER_HOST`, the `kind` network, `/tmp` mount, `fleetshift` network alias, and documented `--privileged` launch setting. If any Kind-only condition fails while basic AIO checks pass, user can disable Kind mode and continue with basic AIO.

### Socket endpoint and bind-source contract

Discovery must keep the host-reachable Unix API endpoint separate from the bind source in the engine's filesystem. Host HTTP `/_ping` validates responsiveness; it does not establish that a macOS-forwarded socket can be mounted by a Linux VM. On native Linux these paths normally coincide. Launch generation uses only the engine-side path and must refuse Kind generation when it is missing, rather than substitute a host endpoint or an arbitrary default.

For managed macOS Podman, use the selected engine's `Host.RemoteSocket.Path` from `podman info`, stripping `unix://`, as in the working root `pd:dev` target (`DEV=true deploy/podman/scripts/start.mjs`), [`ensurePodmanReady`](../../deploy/podman/scripts/common.mjs), and [`compose.yaml`](../../deploy/podman/compose.yaml). `ConnectionInfo.PodmanSocket.Path` from machine inspection remains the host probe endpoint. Match the selected managed connection to the inspected machine by loopback SSH port and identity, not list order or connection-name suffix; rootful/rootless selection must agree with the forwarded API. Require both host ping and read-only `podman machine ssh <matched-machine>` socket existence validation. No curl dependency, image pull, or probe container is required for runtime preflight.

`CONTAINER_HOST` is a client endpoint override, `CONTAINER_CONNECTION` selects a named connection, and `PODMAN_SOCKET` is an absolute engine-side mount override. Overrides never establish local compatibility for arbitrary remote engines. For recognized local Docker Desktop engines, retain the selected host/context Unix endpoint for probing and use the standard VM daemon socket `/var/run/docker.sock` as the bind source. Do not infer engine-side paths for unknown macOS VM providers. Refresh discovery when rechecking prerequisites and hand the same checked snapshot to launch generation after remediation or fallback.

macOS Podman verification covers a successful native PTY preview using the discovered VM-side socket, persistence skipped, Run/Copy declined, and exit 0. An isolated cached-image bind probe confirmed a socket at the container destination and HTTP 200 / `OK`; SELinux required `label=disable` for this unprivileged probe, while the documented Kind launch already uses `--privileged`. Docker Desktop and Linux address-space behavior are fixture-tested; live verification remains outstanding there.

Non-blocking warnings: missing/unsupported Node.js and Docker's limited validation; Kind resource warnings remain proposed (REQ-045). Runtime versions do not gate the PoC.

## Remaining validation and decisions

1. **Linux probes and builds:** Snapshots come from macOS. Verify Linux rootless Podman socket flow, native Docker Engine, and Perry build/runtime behavior; none is validated live yet.
2. **Native execution without Node:** Run the produced executable with Node absent from `PATH` on macOS and Linux. The native build completed and a macOS PTY flow passed, but this specific runtime guarantee has not yet been tested.
3. **ScriptC evaluation:** This experiment is closed for the current PoC and its dependency/build targets have been removed. Initial coverage of Ink 6.8.0 failed on its package graph (including React reconciler/scheduler declarations, JSON package loading, and CommonJS/package resolution); explicit static-package selection still reported blockers. A Rspack bundle was rejected by ScriptC with 243 TypeScript errors across React reconciler/runtime code. ScriptC also lacked lowering for required Node API call shapes, including Unix-socket `socketPath`, and reported missing TTY/subprocess/filesystem APIs. Reconsider only as a separately scoped compiler evaluation; preserve Ink rendering and native execution requirements.
4. **Perry PoC path:** `build-native` pins `@perryts/perry@0.5.1520` and compiles source directly using an isolated build-only copy of Ink and a private local `yoga-layout` package. The branded UI uses genuine Ink `Box` / `Text` JSX, structured colored readiness panels, and bounded arrow-key menus with Enter confirmation. Non-TTY interaction remains numeric/line-based; no alternate screen is used. The local layout subset supports these panels and is tested against upstream Yoga; it does not claim general Yoga compatibility. Perry's native Taffy binding and live Ink `useInput` rendering were investigated but did not reliably sustain repeated interactive layouts, so a small raw-key transport redraws synchronous Ink frames. Hoisted Ink cannot be redirected by an ordinary AIO-local Yoga dependency, so the staging graph isolates the replacement without modifying installed packages or affecting `fleetctl`. Upstream Yoga's WebAssembly path failed in earlier experiments; Rspack bundles also failed at runtime (`react`/`Iterator` reference errors) and are no longer part of this target. Rust/Cargo and a matching unmodified Perry source checkout supply runtime/extension archives missing from the npm distribution, including the `net` extension for the socket probe. See the [AIO build guide](../../client/aio-installation-check/README.md) for native PTY evidence, build commands, resolution isolation, and cache timings. The compiler choice for product distribution remains subject to release review.
5. **Resource policy:** Confirm whether to adopt REQ-045, and determine exact thresholds and their evidence. The observed 6 CPUs/19,953 MiB/150 GiB values are not confirmed requirements.
6. **Polling interpretation:** REQ-019 fixes a 2-second interval and 100 attempts; whether the initial recheck counts and how probe duration affects timing remain ambiguous. No additional timing policy is decided here.
