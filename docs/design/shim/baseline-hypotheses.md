# Baseline hypotheses

**Status: candidate mechanisms, not normative and expected to change.** Each hypothesis shows one way a requirement could be met on unmodified OCM-io v1.4.x and with the resource manager, and names what it rests on. None is implemented by this directory.

**Rules.** [requirements.md](requirements.md) wins. A hypothesis never relaxes a MUST. If a hypothesis cannot satisfy a requirement, the result is a declared gap in [coverage.md](coverage.md) or a deliberate change to the requirement, never a silent exception.

**Evidence** says how far a hypothesis has been checked: *live* means observed on the test environment, *source* means read in code, *proof of concept* means a prototype exists, and *untested* means none of these. Sources are listed in [analysis.md](analysis.md) section 9. **Open** names a question in [decisions.md](decisions.md) section 2 that the hypothesis leaves unanswered.

**Order.** The sections follow the order in which a deployment meets them: observing a hub, enrolling clusters, delivering to them and indexing them, and living beside OCM-io on the same cluster. Section 5 is the form the integration itself takes. Sections 6 and 7 are optional parts. Sections 8 and 9 apply throughout.

## 1. Observing a hub

- **BH-1 Hub connection by read-only watch.** The integration holds one client per hub connection and uses list and watch on the kinds in scope: `ManagedCluster` first, then cluster sets, and `PlacementDecision` where a deployment selects by it. The hub's administrator creates its credential, which has read access to those kinds only. The integration creates no hub object. The operator gives each hub connection a stable identifier, because a hub's address can change.
  *Evidence:* untested as a component; it uses ordinary Kubernetes list and watch. Live for the reach: with a credential for a hub, the hub's `ManagedCluster` objects were listed from where the resource manager runs. *Risks:* watch load on a large hub (N-4); recognizing a hub that was restored at a new address. *Serves:* M-1, M-2, M-3, N-2, S-10.

- **BH-2 Integration state in the management datastore.** Hub connections, observed clusters, enrollments, correlations, exclusions, withdrawals, corrections, and mappings are rows in the resource manager's database. Nothing is written to a hub. They are backed up and restored with everything else. After a restore to an earlier point, facts a hub still holds are read again from the hub, and decisions only the integration holds are as old as the backup, which is reported.
  *Evidence:* untested. Source: a server add-on of the resource manager can define resource types of its own, which the resource manager stores and serves. *Risks:* records that fit no resource type need a place of their own (FC-3). *Serves:* I-1, N-2, R-2, R-4, M-5.

- **BH-3 An observed cluster is a record, not a target.** The integration defines a resource type for a cluster seen through a hub and keeps one record per cluster, named by the hub connection and the cluster's name, with its labels, cluster sets, claims, and conditions. The record is listed and searchable, and the console shows it as a cluster. It is not a target, so placement cannot select it and nothing can be delivered to it.
  *Evidence:* source: a server add-on can define a resource type that is inventory only, report labels and conditions for it, and have a read API served for it. Live: the resource manager's general indexer already copies a hub's `ManagedCluster` objects into its inventory, where the console's search finds them as generic objects. *Risks:* the console lists as clusters only those of its built-in provider (FC-25). *Serves:* M-1, EN-12, IS-1, I-2.

- **BH-4 Declared match in three steps.** A `ManagedCluster` and a cluster the management plane already knows are compared first by a key the deployment declares; then by aliases recorded earlier; then by name, only when exactly one unlinked record on each side carries it. The basis is stored with the link. The natural key is the API address together with the certificate authority: a hub can record both for each cluster, and the resource manager records both for each Kubernetes target. In the test environment that key links each cluster the resource manager created to its `ManagedCluster`.
  *Evidence:* live for the facts; untested as a mechanism. *Risks:* a hub records the address a cluster was registered with, which can differ from the address the management plane uses for the same API server, as it did on an earlier build of the test environment, and it records one only where the klusterlet was given it (E-11). The name step is a heuristic and is reported as one. *Serves:* I-3, I-4, I-5, M-9.

## 2. Enrolling a cluster

- **BH-5 An enrollment is a resource whose delivery produces the target.** The resource manager has no API that creates a target. A target enters through an add-on's declaration, which is fixed, or as the output of a delivery, which a later delivery can replace and which is removed with the fulfillment that owns it. The candidate uses the second path, as the built-in cluster provider does. An enrollment is a resource of the management API, defined by the resource manager's own handling of Kubernetes clusters and not by the integration (BH-19). Accepting it runs a delivery that applies nothing to the cluster: it verifies what was presented (BH-9), stores the credential in the resource manager's secret store, and reports a target of the ordinary Kubernetes type, with the cluster's address, its certificate authority, a reference to the stored credential, and the labels of BH-14. From then on the resource manager's existing Kubernetes delivery and indexer treat the cluster like one it created. Deleting the enrollment removes the target. Target names are unique across the installation, so the generated name combines the hub connection and the cluster name (I-7).
  *Evidence:* source and live for how a target enters: the cluster targets in the test environment are delivery outputs that carry exactly these properties. Untested for a cluster the resource manager did not create. *Risks:* it is a workaround for a missing API (FC-1, FC-22); a target's labels change only when the delivery runs again; it spends several datastore records per cluster; it needs one built-in target that enrollments are placed on, as the built-in provider has. *Open:* OQ-10. *Serves:* M-10, EN-11, EN-13, I-7.

- **BH-6 The access piece of the direct form.** The piece is a service account and a binding of that account to a role the administrator chooses. The management plane receives a time-limited token for the account at enrollment and, before the token expires, asks the cluster's API for the next one with the token it holds. Nothing has to keep running on the cluster. Removing the binding or the account ends the access from the cluster's side.
  *Evidence:* live, from where the resource manager runs, with a token for such an account on a cluster the resource manager did not create: list, watch, discovery, and server-side apply succeeded, and the holder obtained a fresh token from the cluster's API. After the account and its binding were removed, the token was refused at once. In these checks the account was bound to the cluster-administrator role. *Risks:* a narrower role has to include the right to request a token for that one account, and was not exercised; if the management plane is away for longer than a token lives, the cluster has to present a credential again (BH-7, BH-8). *Open:* OQ-13. *Serves:* EN-2, EN-7, EN-8, EN-9.

- **BH-7 Roll-out through OCM-io's add-on mechanism.** The hub's administrator applies two objects to the hub once: an add-on template that contains the access piece and a small enrollment agent, and the add-on's registration. Enabling the add-on for a cluster, by name or through the add-on's install strategy and a `Placement`, makes OCM-io deliver the template to that cluster. The agent requests a token for the service account and presents it to the management plane with the cluster's name and certificate authority. The address comes from the hub's record of the cluster (BH-9), because an agent inside a cluster does not know the address the cluster is reached at from outside. The service account and its binding carry OCM-io's annotation that leaves a manifest in place when its add-on is removed, so disabling the add-on for a cluster removes the agent and every hub object for that cluster and leaves the access piece.
  *Evidence:* live on unmodified OCM-io v1.4.0, with a stand-in for the management plane's receiving side: two hub objects in total, and two for each cluster while enabled, which are the add-on's enablement and the work OCM-io creates to install it; two clusters enrolled within 12 seconds of being enabled; after disabling, no hub object for the cluster, the access piece still in place, and the credential still working; left enabled, the agent presented a fresh credential after 25 minutes. Selection by `Placement` is read in source and was not exercised. *Risks:* the credential travels from the cluster to the management plane, so the receiving side has to authenticate the sender and be authenticated by it (FC-23), which the stand-in did not do; the template can ask only for what OCM-io's work agent is allowed to grant on that cluster. *Open:* OQ-12, OQ-15. *Serves:* EN-4, EN-5, N-2, K-12, C-1.

- **BH-8 Roll-out with no hub object.** The management plane generates, for a cluster or a set of clusters, the manifest of the access piece and a one-time secret for presenting the result. The manifest is applied by hand, by the pipeline that builds the cluster, or by a GitOps agent on the cluster. The credential is then presented by a command-line step or by the same small agent as in BH-7. A cluster that no hub knows is enrolled the same way, with its address given by whoever enrolls it.
  *Evidence:* untested as a flow. The access piece is two objects of built-in kinds, which any tool that applies manifests can deliver. *Risks:* a step per cluster unless a pipeline or a GitOps tool carries it. *Serves:* EN-4, EN-5, M-8, EN-13.

- **BH-9 An enrollment is checked against the cluster and against the hub.** Before a target is created, the management plane calls the cluster's API at the given address, trusting only the presented certificate authority and using the presented credential, and asks the cluster which identity the credential belongs to. For a cluster in the scope of a hub connection, the integration also compares the address and the certificate authority with the client configuration the hub records for that `ManagedCluster`. Where the route issued a one-time secret, it has to be presented as well. Any mismatch creates nothing and is reported.
  *Evidence:* live for the facts: the address and certificate authority the hub records for each of the three clusters of the test environment were the ones the cluster answered with from where the resource manager runs, and the certificate authority each enrollment agent presented was the same. Untested as a mechanism. *Risks:* the hub's record exists only where the klusterlet was given it (E-11), and may hold an address the management plane cannot reach. *Open:* OQ-15. *Serves:* EN-6, I-3.

- **BH-10 A hub is enrolled through its own registration.** A hub that is registered with itself as a managed cluster receives the access piece through the same routes. Its role grants reading only, and the control-plane namespaces of OCM-io and of the management plane are excluded from delivery. Indexing a hub is narrowed to the kinds a deployment selects, because a hub holds objects for every cluster.
  *Evidence:* live: a hub was registered with itself using unmodified OCM-io and enrolled by the add-on of BH-7 like any other cluster. A read-only role and narrowed indexing were not exercised. *Risks:* indexed whole, a hub's per-cluster objects are copied into the management datastore (N-12, FC-28). *Open:* OQ-4. *Serves:* EN-14, X-9, T-9.

- **BH-11 Withdrawal from either side.** Withdrawing a cluster deletes its enrollment, which removes the target, the stored credential, and the indexer, and records that the cluster is not to be enrolled again even while an add-on is still enabled for it. The access piece is then removed on the cluster's side. If the access piece is removed first, the cluster's API refuses the credential, and after a confirmation the integration reports the cluster as withdrawn instead of retrying. Delivered workloads stay unless their intent is deleted.
  *Evidence:* live for the cluster's side: once the service account and its binding were removed, calls were refused at once, and the hub went on reporting the cluster as available. Untested as a mechanism. *Risks:* the resource manager keeps the inventory rows of a cluster that is gone (FC-28); telling a withdrawn cluster from a broken one needs more than one refused call. *Serves:* EN-9, M-5, IS-6.

## 3. Delivering and indexing

- **BH-12 Delivery on the direct path with the enrolled credential.** The resource manager's existing Kubernetes delivery applies with server-side apply under one field manager name and never forces. It creates nothing on a hub and no custom resource on the cluster. For an enrolled target it applies with the stored credential, under the rule the target declares. Today that rule has one form: intent that carries a verified signature, on a target that carries trust settings. Intent without a signature is applied with the caller's own token, which a cluster accepts only if its API server trusts the management plane's identity provider. The candidate gives an enrolled target its trust settings at enrollment, and adds an explicit, recorded grant as a second form if OQ-14 is answered that way.
  *Evidence:* source, with the resource manager's unit tests for a valid signature, an invalid one, and a target without trust settings. Live: a deployment of a `ConfigMap` and a `Deployment` to a cluster the resource manager created was active after 14 seconds, with no object on the hub and no custom resource on the cluster; the caller's token was refused by a cluster created outside the resource manager; the same server-side apply, made by hand with an enrolled credential, succeeded on that cluster. The two cluster targets of the test environment carry no trust settings at present, which the unit tests show is refused for signed intent. *Risks:* delivery to an enrolled cluster by the resource manager itself has not been run, because no such target can be created yet. *Open:* OQ-14. *Serves:* W-8, W-2, N-11, S-3, S-16.

- **BH-13 The resource manager's own agent, rolled out by the same routes.** In the agent form the access piece is the resource manager's agent. It connects out to the management plane, authenticates as its cluster, applies deliveries with a service account that stays on the cluster, and runs the indexer locally, sending changes. It is installed and upgraded through the routes of BH-7 and BH-8. It applies under the same field manager name as the direct path, so a cluster can change form without a change of owner on what is applied. During the change, one path is active for each workload at a time, and the period is reported.
  *Evidence:* source: the agent's service is defined in the resource manager's API and is not served, and there is no agent. The resource manager's design documents describe both. Live, for OCM-io's work agent only: two appliers that use one field manager name share a resource, and the one that remains can change it without force. *Risks:* it is the largest unbuilt piece (FC-29); an agent has a version of its own to keep within a declared skew (K-11). *Open:* OQ-16. *Serves:* EN-3, W-1, S-12, S-15, N-12.

- **BH-14 Hub facts as target labels.** The labels a hub holds for a cluster, its cluster set, and its cluster claims become labels on the cluster's target, set at enrollment and refreshed when they change on the hub. The resource manager's exact-match selection then works with the labels people already use. Expressions, claim selectors, and taints and tolerations do not survive, and are declared lost. To keep them, a deployment selects by a `Placement` the hub has already decided: the integration reads its `PlacementDecision` objects and keeps one label on each decided target, which exact-match selection can use. A claim that collides with a label key resolves by a declared precedence and is reported.
  *Evidence:* source for the resource manager's exact-match selector. Live for the starting point: the targets of the test environment carry no labels. Untested as a mechanism. *Risks:* a label reaches a target only when the enrollment's delivery runs again (BH-5), until targets can be updated (FC-1); a decision copied as a label lags the hub by the freshness budget. *Serves:* M-4, M-3.

- **BH-15 Two sources of inventory.** Facts about every observed cluster come from the hub objects the integration watches. Resources on an enrolled cluster come from the resource manager's existing indexer, which is started for the target with the enrolled credential in the direct form and which the agent runs in the agent form. Nothing is collected from inside a cluster that is only observed.
  *Evidence:* live for the indexer on the clusters the resource manager created, about 840 objects for two small clusters, and for a watch with an enrolled credential on a cluster it did not create. *Risks:* the indexer watches every kind apart from a short deny list, for every target, inside the resource manager (N-12); rows of a cluster that has left are kept (FC-28). *Open:* OQ-4. *Serves:* IS-1, IS-2, IS-3, IS-6.

## 4. Two systems on one cluster

- **BH-16 Ownership by field manager, never forced.** The resource manager applies with server-side apply under its own field manager name and never forces. OCM-io's work agent applies under another. A field that one of them owns is refused to the other, so each resource has one owner and a conflict names it. Whether an OCM-io work can take a resource from the resource manager depends on the work's own update strategy: server-side apply without force fails and names the resource manager, and the default update strategy overwrites.
  *Evidence:* live, on one cluster served by both: resources that only one of them delivered were unaffected by the other; the resource manager's apply onto a resource OCM-io had delivered was refused; an OCM-io work with server-side apply and no force onto a resource the resource manager had delivered failed and named it; an OCM-io work with the default strategy overwrote that resource, and deleting the work then deleted it. *Risks:* the resource manager retries a refused apply without limit and gives no reason through its API (FC-30); it does not notice the overwrite (BH-18). *Serves:* W-14, W-15, W-13, C-5.

- **BH-17 A move by shared ownership.** To move a unit of workload from OCM-io to the resource manager, an intent with identical content is created in the resource manager. Its apply succeeds because nothing differs, and the resource then has both owners. After that is verified, the work's owner deletes it on the hub with OCM-io's orphan delete option, which leaves the resource in place with the resource manager as its only owner. The way back mirrors it: an OCM-io work with identical content, then the resource manager's intent deleted with its resources left in place.
  *Evidence:* live: the move to the resource manager kept the resource's identity throughout. The way back did not hold, because the resource manager has no delete that leaves resources: the resource was removed within two seconds, and OCM-io restored it, as a new object, four and a half minutes later. *Risks:* the content has to be identical in every field either side sets; the hub's work belongs to its writer, who retires it (W-11); the way back needs FC-27. *Open:* OQ-11. *Serves:* W-7, X-3, X-4, W-17, W-11.

- **BH-18 Watching what was delivered.** For each delivery the management plane compares what it applied with what the cluster's index now shows: whether each resource exists, and whether the resource manager still owns the fields it set. A difference marks the delivery as changed, taken over, or removed, per target. Where the intent's policy says so, the content is applied again without force, which restores a removed resource and fails visibly on one that another writer now owns.
  *Evidence:* live for the need: after an OCM-io work took over and then removed a resource the resource manager had delivered, the deployment was still reported as active 45 seconds later, when the check ended. Untested as a mechanism. *Risks:* the comparison depends on the index being current for that cluster. *Serves:* W-16, W-5.

## 5. The integration as an extension

- **BH-19 A server add-on and a console plugin, on a general capability.** The integration has the two halves of a resource manager extension. The server add-on declares the hub connection and the observed cluster as resource types, runs the hub watch, checks each enrollment against the hub's record, and keeps the labels of enrolled clusters current. The console plugin adds a set-up step that connects a hub, an entry that enrolls clusters, a tab on a cluster's page with what its hub knows, and a renderer for search results. Verifying a cluster against itself, storing and renewing its credential, creating its target, and starting its indexer are not the integration's: they belong to the resource manager's own handling of Kubernetes clusters, which takes in any existing cluster, with a hub or without one.
  *Evidence:* source: server add-ons declare resource types, delivery, and inventory, and the console has extension points for routes, set-up steps, cluster providers, onboarding actions, cluster detail tabs, and search result renderers. Live: the console's extensions page carries a demonstration step for connecting an external provider. *Risks:* server add-ons and console plugins are built into the resource manager today (FC-2), and an add-on has no handle on targets (FC-1); the console's cluster list and cluster page are tied to the built-in provider's type (FC-25). *Serves:* A-12, EN-13, U-10, EN-11.

## 6. Driving from Kubernetes

This part is optional. Nothing in it is needed to enroll a cluster or to deliver to it.

- **BH-20 `ManifestWorkReplicaSet` as a driving object.** A driver watches `ManifestWorkReplicaSet` objects on the Kubernetes-facing surface. For each one it maintains an intent in the resource manager: the work template becomes the manifests, the referenced placements decide the targets, and the rollout strategy maps to the resource manager's rollout. It writes only the object's status. No per-cluster `ManifestWork` is created. Selection can stay with OCM-io: the driver reads the `PlacementDecision` objects that OCM-io's placement controller writes and passes the decided clusters to the resource manager as an explicit list, which preserves every `Placement` feature at the cost of one small object per hundred clusters. A decided cluster that is not enrolled receives nothing and is reported.
  *Evidence:* live: a v1.4.0 hub serves the API and runs no controller for it by default. Source: the feature gate that starts that controller is off by default at v1.4.0 and on by default in OCM-io's API repository after that release. Untested as a mechanism. *Risks:* the resource manager's rollout is immediate only, so progressive strategies are approximated or refused (W-12); where OCM-io's own controller for this kind runs, the kind cannot be driven on that hub (K-5), so the driver needs a surface without that controller or the option in E-6; tools that list the per-cluster works find none, because per-target records are not written to any Kubernetes API (GO-7). *Open:* OQ-3. *Serves:* K-5, GO-2, GO-4, GO-7, GO-8.

- **BH-21 Projections on a surface without competing controllers.** Where no hub remains, a projector writes `ManagedCluster` and `PlacementDecision` objects from management-plane state for the scopes that select them, and marks each as a projection. A projected `ManagedCluster` on a hub whose registration controller is running would be treated as a real cluster with no agent. Projection of that kind therefore needs a surface where that controller does not act on it.
  *Evidence:* untested. *Risks:* consumers that expect the hub's controllers to keep an object's status fresh; cost per projected object (K-12). *Serves:* K-6, K-7, GO-8, I-6.

- **BH-22 Declarative apply and pipeline identity.** The management API gains one idempotent operation that creates or updates an intent from a document, reports the difference in a dry run, and deletes exactly one unit. A pipeline authenticates as a workload through the identity provider. Where its intent is signed, the signature is verified before platform credentials apply it.
  *Evidence:* source: signed intent is verified today; the deployment API has no update. *Risks:* an update changes a fulfillment's generation, which today only delete and re-create can do. *Serves:* GO-9, GO-10, S-3, S-7.

## 7. Serving OCM-io agents

This part is optional. An enrolled cluster needs none of it to stay managed when its hub is retired. It is for a deployment that retires a hub and keeps the klusterlet as a cluster's only agent.

- **BH-23 The management plane as a work source.** OCM-io's SDK defines the server side of its event-based protocol: a broker, and for each resource type a service that lists resources for an agent, handles the agent's status updates, and notifies the agent of changes. OCM-io's hub implements those services over the Kubernetes API. The candidate implements them over the management datastore. Each delivery to a cluster is presented to that cluster's work agent as a `ManifestWork` in the protocol's form, and the agent's status updates become delivery results. No `ManifestWork` is stored in any Kubernetes API.
  *Evidence:* source for the seam; a resource manager proof of concept presents a delivery as an in-memory `ManifestWork` view and drives OCM-io's own manifest controller with it. The endpoint is unbuilt. *Risks:* protocol conformance and version skew (K-11); per-cluster authentication and authorization (S-12); resynchronization after a reconnect; the work agent keeps one applied-work record on the cluster for each delivery (W-2). *Open:* OQ-2. *Serves:* K-3, W-4, W-8.

- **BH-24 Changing a cluster's source while eviction is held off.** In the baseline, OCM-io's klusterlet operator sets the work agent's source from the registration driver, so a cluster's registration and its work source move to a gRPC server together. A work agent that follows a new source treats applied work from the old one as unmanaged and evicts it after a grace period, 60 minutes by default. At eviction it keeps every resource that applied work from the new source also owns ([analysis.md](analysis.md) section 7.8). The candidate procedure is: raise the klusterlet's eviction grace period to the value that disables eviction; confirm the hub holds no work for the cluster that the management plane would not deliver; have the management plane hold an equivalent delivery for every work the cluster has; switch the klusterlet's connection; verify that each applied resource is owned by applied work from the new source; then restore the grace period, which lets the old applied work be evicted. Switching back before that last step is the rollback.
  *Evidence:* source for the coupling and for the agent's rules. Live on an unmodified v1.4.0 klusterlet: the procedure was carried out for a change of the hub's address, in both directions, and the applied resources kept their identity and their running pod throughout. With constructed applied-work records, a resource that only the previous source owned was deleted, and a started eviction was cancelled when its work returned. Not exercised: a gRPC source, and a new source that holds different content. *Risks:* a cluster whose add-ons still deliver through the hub cannot move, because an agent follows one source (K-8); a resource the new source delivers differently is changed, and one it does not deliver is deleted; an agent that registers again stops renewing its lease until it is approved, so acceptance has to be arranged before the switch; the procedure changes two klusterlet settings, the connection and the grace period, and a rollback has to restore both. *Open:* OQ-7. *Serves:* W-7, X-6, M-7.

- **BH-25 Registration over gRPC against the management datastore.** A klusterlet is configured with OCM-io's gRPC registration driver and the management plane's endpoint. The management plane implements the protocol's registration services over its datastore: a join request becomes a pending membership record, acceptance is a management API operation with attribution, the certificate is issued by the management plane, and lease renewals update freshness. No hub object is involved. In the baseline the work source moves at the same time (BH-24).
  *Evidence:* source: OCM-io's gRPC registration proposal names a store other than the Kubernetes API as a future possibility. Unbuilt. *Risks:* breadth, since the protocol covers clusters, certificate requests, leases, events, add-on status, and token requests; OCM-io add-ons register against hub APIs and cannot follow (K-8); a cluster is reported unreachable if acceptance takes longer than its lease allows ([analysis.md](analysis.md) section 7.9). *Open:* OQ-7. *Serves:* M-7, K-3, S-12.

## 8. Tenancy, security, and history

- **BH-26 Tenant keys on every row.** Every table that holds tenant data carries the tenant and workspace. The API enforces scope on every request, and on PostgreSQL row-level security enforces it again in the datastore. Role assignments are rows scoped by workspace, resource type, and operation, and the API checks them on every request. The same keys are the partition keys N-10 asks for.
  *Evidence:* untested; the current schema has neither key. *Serves:* T-1, T-2, T-6, S-14, N-10.

- **BH-27 Hub connections as the first tenancy boundary.** Until workspaces are enforced, visibility is provider-only. When they are, a hub connection maps to a tenant or a workspace by declaration, which preserves the separation that separate hubs gave.
  *Evidence:* untested. *Open:* OQ-6. *Serves:* T-3, T-7, T-8.

- **BH-28 Tokens in memory, with a pause.** A user's token is held in the memory of the replica that accepted the request and is never written to the datastore or the workflow history. If that replica restarts or the token expires, the delivery pauses and an authorized user resumes it. Unattended work uses signed intent with platform credentials or a delegated workload identity. Where the user's token is presented, the platform needs only the target's address and trust bundle, not a credential of its own.
  *Evidence:* source: pause and resume exist; the token is persisted today. *Risks:* with several replicas, the replica that holds the token must be the one that delivers; a cluster that already exists accepts a user's token only if its API server trusts the management plane's identity provider, which enrollment does not arrange. *Serves:* S-3, S-4, S-5, S-15.

- **BH-29 History as append-only tables.** Every change to management state appends a row with the principal, the time, the subject, the previous and new version, and the source. History of observation is a separate, time-partitioned table with declared retention.
  *Evidence:* untested. *Risks:* write volume (N-5). *Open:* OQ-5. *Serves:* IS-7 to IS-10, S-2.

## 9. Recovery and scale

- **BH-30 Restore, then reconcile by generation.** After a restore, the management plane compares the generation it holds for each delivery with what enrolled clusters and agents show. Where a cluster holds a newer generation than the restored datastore, nothing is delivered and the divergence is listed for an operator. A restored credential that no longer works marks its cluster as needing enrollment.
  *Evidence:* source: deliveries carry a generation today. The comparison is untested. *Open:* OQ-8. *Serves:* R-4, W-3.

- **BH-31 A capacity model from measurement.** The capacity model is produced by loading a datastore to each profile and measuring rows and bytes per cluster, intent, delivery, and inventory item, on both backends, and by counting what the management plane holds open for each enrolled cluster in each access form.
  *Evidence:* a first measurement of the SQLite store at three targets ([analysis.md](analysis.md) section 2.1). No profile has been loaded. *Open:* OQ-9, OQ-16. *Serves:* N-3, N-12, O-6, V-5.

## 10. A possible first increment

BH-1 to BH-9, BH-11, BH-12, BH-14, BH-15, and BH-19 are enough for the first increment in [topologies.md](topologies.md) section 9: hubs observed, the clusters that opt in enrolled in the direct form, and the resource manager delivering to them and indexing them itself, with no hub object for any delivery. BH-16 is what already holds on a cluster that both systems deliver to. BH-10 adds a hub's own objects, BH-18 adds the watch on what was delivered, BH-17 adds moves between the two systems, BH-13 adds clusters that accept no inbound connection, and BH-29 adds history. Sections 6 and 7 are taken up only where a deployment wants them.
