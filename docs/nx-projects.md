# Adding an Nx project

Shared quality behavior belongs in [nx.json](../nx.json). Project configuration
selects that behavior and declares project-specific commands and dependencies.
Use this recipe when adding a project or introducing another kind of check.

## Select a profile and register the project

Add a `project.json` at the project root, with a unique `name`, a short
`metadata.description`, and the appropriate quality tag:

| Project               | Quality tag       | Starting examples                                                                           |
| --------------------- | ----------------- | ------------------------------------------------------------------------------------------- |
| Go module             | `type:go-module`  | [deploy-aio](../deploy/aio/project.json), [Go tooling](../tools/golangci-lint/project.json) |
| JavaScript/TypeScript | `type:js-project` | [common](../sdk/common/project.json), [CLI](../client/cli/project.json)                     |
| Protobuf module       | `lang:proto`      | [proto](../proto/project.json)                                                              |

Register npm packages in the root `package.json` workspaces too. Every Go module
outside `poc/` and deliberate fixtures needs its own Nx project at the module root.
Keep scope/architecture tags alongside the quality tag; they serve different purposes.

## Keep agent context current

The root `AGENTS.md` project list uses `metadata.description` for the overview and
optional `metadata.additionalAgentInstruction` for brief guidance or a pointer to
project instructions. The latter accepts a string or an array of strings:

```json
{
  "metadata": {
    "description": "Resource manager API server.",
    "additionalAgentInstruction": "See server/AGENTS.md for guidance."
  }
}
```

After adding or renaming a project, or changing this metadata, run
`npx nx run ocm-fleet:generate-agents` and include the resulting `AGENTS.md` change.
The target rebuilds its **Nx Projects (autogenerated)** section from the Nx graph;
edit the project metadata to update generated entries.

## Opt into the shared lifecycle

Add these entries to `targets`; empty entries inherit their implementation from
`nx.json`. Tags alone do not create targets. Missing targets can otherwise be
silently skipped by workspace aggregation.

```json
{
  "fmt": {},
  "verify": {},
  "fix": {},
  "fix:lint": {},
  "refresh:inputs": {},
  "check": {},
  "lint": {}
}
```

JavaScript/TypeScript projects also need `"lint:format": {}` and a project-specific
ESLint command/executor on `lint`. Go's `lint` is inherited. Protobuf projects
provide Buf `fmt`/`lint` commands and a no-op `fix:lint`, as in the example.

| Target   | Contract                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| `fmt`    | Apply formatting and import organization, then refresh Nx's file hashes.                                            |
| `verify` | Format first, then check the resulting source in a fresh Nx invocation.                                             |
| `fix`    | Format, apply broader supported linter fixes, then check. Review its diff.                                          |
| `check`  | Read-only lint, formatting, normal tests, component tests, and type checks that the project provides. CI uses this. |
| `lint`   | Report findings without editing source. Go and Buf also check formatting here.                                      |

Leave common commands and ordering in `nx.json`. Source-rewriting targets and
`verify` must not be cached. Custom rewrites must also refresh the file hashes.

## Declare the project's capabilities

- **Go tests:** provide `test` for each module, even if it currently has no test
  files. Use `GOWORK=off` when the module must remain isolated.
- **Unit tests:** provide `test` when test files exist. For the shared root Vitest
  configuration, add `test:vitest` and `"test": {}`. Custom test setups keep their
  own command and inputs. End-to-end specs belong to `test:e2e` instead.
- **Styles:** projects with CSS/SCSS provide `lint:css` and `"fix:css": {}`.
- **Browser components:** provide `test:ct` for `.ct.tsx` files. Install Playwright's
  Chromium browser locally. Declare only the prerequisites the suite consumes:
  browser aliases can use source, while Node-side package imports may need a build.
- **Type checks:** add `typecheck` where supported; `check` includes it automatically.

Keep integration and end-to-end suites explicit, outside normal `check`/`verify`.
Dependencies on builds or generated assets belong in `dependsOn`, not in a
developer's remembered sequence of commands. Verify those dependencies once with
the relevant build outputs absent and `--skip-nx-cache`.

For cacheable checks, include source, fixtures/embedded assets, dependency sources,
configuration, tool versions, and execution settings that affect results. Retain
the shared named inputs (`goLintConfig`, `eslintConfig`, `formatConfig`, and
`jsRuntime` as applicable) when overriding `inputs`; arrays replace inherited
values. Declare build outputs so cache restoration can recreate them.

## Verify registration

```bash
npx nx run ocm-fleet:lint:nx-projects
npx nx run <project>:verify
npx nx run ocm-fleet:generate-agents
```

`lint:nx-projects` runs during workspace `check` and CI. It inspects the current
source inventory and resolved Nx graphs without running project tools. It catches
unregistered Go/npm projects, missing tags/targets, checks omitted from the graph,
unsafe standard caching settings, and discovered tests/styles without their targets.
It always runs so an unregistered file cannot hide behind an old cache hit.
The companion `test:nx-projects` exercises these rules using Nx's real graph builder.

Placeholders or deliberately unsupported projects must explain their exemption in
`metadata.quality.exemption`, for example `"Backend implementation is deferred."`.
Remove it when activating the project. Fixtures, generated assets, and standalone
`poc/` experiments are outside this policy; an exemption never covers an unregistered
nested Go module or npm workspace.

The validator checks conventions, not the completeness of every custom cache key
or runtime dependency. Those still need review and focused tests.
